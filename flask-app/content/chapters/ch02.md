## BAsh (or *The Bourne Again Shell)

The Bourne Again Shell (hereafter, *bash*). Why is it born again? Why is it spelled like that?

Ten layers of irony.

Bash was created in 1989 by Brian Fox. It built on the work of a Bell Labratories researcher Stephen Bourne (hence, Bourne *again*). The original shell (or *sh*) was Portable Operating System Interface (POSIX)conforming, meaning that it conforms to a set of standards across all UNIX devices. Though this is beyond the scope of this class, suffice to say that when you see POSIX, think "scripting and basic utilities. Bash continues to be the default shell installed in every distro as it is part of the GNU kernel files. However, like all 40 year old technology there have been innovations due to how users have decided they want their shells to behave; the most popular competitior being <a href="https://ohmyz.sh/" target="_blank" rel="noopener noreferrer" aria-label="navigate to the z.sh homepage">z.sh</a>. Shell come in different shapes and sizes and colors and functionality. When deciding on a shell to use, factors one should use are considerations like purpose. Bash is as popular as it is due to its incredible performance, requiring the use of very little memory and CPU. Because of this it can work much faster than a heavier shell with more user comfort features. We can discern the difference between bash and something like z.sh like the difference between a military High Mobility Multi-purpose Wheeled Vehicle (HMMWV) and a commercial-grade Hummer H3. That HMMWV is meant to perform under war-time conditions and to always plug along on the battlefield, but it isn't considered fun to drive, or comfortable by any means. While the H3 is a comfortable ride meant for creature comforts. They may look the same, but they are built with different purposes in mind.

## Environment/Shell Variables

Have you ever sat at someone else's computer and their file hierarchies are organized incorrectly, and they have their mouse scroll too slow, and they use sticky keys, and every other setting that someone else uses that makes their terminal unusable to you? Those configurations are saved and stored in what is called an *environment variable* and it works on a *key-value* pair. A key-value pair can be thought of like a database of information:

```yaml
superhero: Captain America
   first_name: Steve
   last_name: Rodgers
   birthdate: 07/04/1918
   height: 74 inches
   weight: 240 pounds
```

The key is used to identify the data, the value is the data itself. The keys must be unique to the object, while the data is not. Could Steve Rogers have more than one date of birth? Of course not, but he could have his birth certificate issued on the same day of his birth, right?

```yaml
superhero: Captain America
    - birthdate: 07/04/1918
      birth_certificate_issued: 07/04/1918
```

This is the extent of the depth that we will dive into data structures for this course. There are entire courses worth of knowledge and an entire course of study dedicated to Data Structures and Algorithms, and if how data is managed is interesting you should look for specific material about that.

Environment variables are stored at the operating system level, available to any user or process - and stores information that the operating system needs to know to continue operations or to feed to other commands. Run a ```printenv``` command in your **server-vm** or **client-vm**, and see the information that is pertinent to your current operating system
```bash
printenv
```

The output should include information that we should already recognize as being particularly relevant (output truncated):

```bash
[vagrant@server-vm ~]$ printenv
SHELL=/bin/bash
HISTCONTROL=ignoredups
HISTSIZE=1000
HOSTNAME=server-vm
PWD=/home/vagrant
LOGNAME=vagrant
XDG_SESSION_TYPE=tty
MOTD_SHOWN=pam
HOME=/home/vagrant
LANG=en_US.UTF-8
USER=vagrant
PATH=/home/vagrant/.local/bin:/home/vagrant/bin:/usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin
```
We can see the working directory, the home directory, the shell version that we are using, the user profile under which ```printenv``` was executed, and the files on PATH. Obviously, since we know where these are stored, perhaps we can change them? Changing an environment variable requires that we understand where that configuration or variable is stored. During the user creation process, key-value pairs about the user's configuration is stored in the **/home/.bashrc** directory (if the user is using bash).

### Aliases

Among all the variables stored in the **~/.bashrc** file is the *alias* information. A user is welcome to change the name of any command in the shell to something else. Though we will learn more about this later, the command ```mkdir``` is five characters long - and I don't like typing five characters when I can shorten it and not collide with other commands. Be careful about creating aliases, especially if you're unfamiliar with the command line operations as you can create name collisions that you will eventually have to track down and fix, since there are few controls wrapped in the Linux kernel.

### Locating, Searching, and Reading Files

More end-user focused operating systems like MacOS, Windows 11, and ChromeOS focus on making searching for files and through files a primary focus - those operating systems were built with that in mind and much of their performance is geared to that. Command line operations using Microsoft's PowerShell or bash require that we shift our traditional document-focused, GUI-focused paradigm to a text-file based one instead. Because we don't have anything to click, we have to learn how to ask the computer for what we want - we want to find, and we want to read.

There are more utilities written to help manage files than likely any other utilities for the Linux kernel. The gold standard among them are ```sed```, ```awk```, and ```grep``` for finding text and replacing it; and ```more```, ```less```, ```head```, ```tail```, and ```cat``` for reading the contents of files. The possibilities for how each individual administrator will use ```sed```, ```awk```, and ```grep``` are essentially endless - we couldn't possibly know what utilities your Linux environments will run or what you will write, and the exact nature of how you will use these commands will be determined by the environment that you are in.
