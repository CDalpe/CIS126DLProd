## Introduction to Services

Behind the scenes of what a user sees, there are hundreds of tiny applications that are running at any given time. They are performing actions like file scanning, memory maintenance, or waiting to support user activites. While the primary purpose user devices and server-level devices can be different, a computer does not discriminate, if all the right resources are present, and the pre-conditions for running a program or application are met a computer will run it. It is perfectly reasonable for a user machine to act as a web server (that is what you are seeing right now). This machine is running Python and Flask to deliver /content/chapters/ch02.md when a web browser requests the resource using HTTP to port 80 (don't worry if you don't understand this now).

These little services that the computer often starts and run siltenly in the background are called *daemons*, so named for the little helpers to the Greek Gods in traditional Greek Mythology. Daemons and services, for all intents and purposes are interchangeable. Often times in the professional computing world, there will be more than one word for a computing concept or activity. This grows from the parallel development. Over time one will lose out in the common parlance. The Daemon/Service is one of those times. Hereafter, for simplicity's sake, *services* is the term we will use.

Services can be launched one of two ways; by parent process or by administrator manually starting it. An administrator or user manually kicking off a service and its implications are fairly self-explanatory, the service can perform any actions that the account that launched it can. What would happen if a parent process kicks off a service, what then? The child process inherits the permissions of the parent process. Since the first process that kicks off is the init process with permissions of SYSTEM - **this means that anything started on the machine that an admin does not account for is potentially incredibly dangerous** *(more on this later.)*

Many applications can be servicized by applying the "--daemonize" option - this means they will be turned into services and can be controlled like services. That functionality is often built in to programs that developers know admins will want that to be the standard behavior. But for others an admin will have to ask the operating system to perform that action for them.

## Performing Actions for Clients
The primary use for computers today is to perform actions in a networked environment. Though we will discuss managing network connections in Chapter 7, we need to discuss the basics of the TCP/IP stack. *Transmission Control Protocol/Internet Protocol* grew out of a need for computers to connect and perform actions for each other, much in the same way that humans specialized during our civilzation's beginnings. The giants of early computing, on who's shoulders we now stand made decisions about how the world of computing would agree on standards. They have the *Request for Comment* (RFC) process, where a developer comes up with an idea of new rules or standards that might be of some usefulness or import to the world at large. The *Internet Engineering Task Force* (IETF) is the standards body that discusses these rules, standards, procedures, or methods. Some RFCs are foundational; such as RFC1918 - the basis for Private IPv4 Addressing in Class A, B, and C Networks. Some are, like all things with computers, downright silly. Take for example, RFC1149 *IP over Avian Carriers with Quality of Service*. 

Spoiler: its carrier pigeons.

The standard was later expanded to include... encapsulation by way of predator bird.

The TCP/IP stack is broken down into 65,536 ports (or 2<sup>16</sup>). These ports are broken into three sections, System (or Well-known), Registered, and Dynamic. Client machines have to know to what port to send the request when they want a response. If a machine didn't have that guidance, it would be the equivalent of knocking on all 65,536 doors in a building and waiting for a response, that could take 327,680 seconds to get a failed response (or about 91 hours). The solution is that we have the RFC to guide us on what port address we should use. CompTIA's Linux+ tests on the following ports/protocols:

These common port/protocol mappings are called the *Well-Known Ports* - and they consume ports 0-1023 of the stack. After the well-known ports come the *Registered Ports* (1024-49151) - so named because they are registered to a software manufacturer for a specific application/purpose. In this range we have Microsoft's SQL Database, Airplay, VNC, and thousands of other applications that need listeners. Some of these will have an official registration, some are unofficial. Last we have the *Ephemeral Ports* (49152-65536), these are designed to be the source ports.

But here's the thing about rules: Nobody says you have to follow them. These are simply conventions and agreements that are used commonly in the industry to simplify communication. An administrator is free to run whatever service they like on whatever port strikes a fancy, provided that they are willing to live with the consequences - such as having to configure a common protocol to use a different port manually on every machine, or having port collisions.

Let's imagine that you have been asked to perform an internet search, The TCP/IP protocol runs on a set of rules for how machines will perform so you can connect out and ask your question (*this is simplified and does not take into account environment complexity*):

<ol id="list">
    <li>The client machine picks a port from its own <em>Ephemeral Ports</em> at random (<em>50505</em>) and uses the web browser application to request the IP information for "google.com" from the pre-configured DNS server on port 53.</li>
    <li>The DNS server receives the request on port 53 from the client machine, then looks in its own records for an A record of "google.com", if the local DNS server has the record it will return it to the client machine and close the connection.</li>
    <li>The client machine receives the A record, then picks another port at random from its <em>Ephemeral Ports</em> (61578) and uses that as the source port for the web browser to send an HTTP GET request to the IP address's port 443.</li> 
    <li>Google has decided that it will run its homepage on port 443, so it returns the HTML/CSS/Javascript on their home. After returning with the requested files it closes the connection from 443 to the client's 61578 port.</li>
</ol>
